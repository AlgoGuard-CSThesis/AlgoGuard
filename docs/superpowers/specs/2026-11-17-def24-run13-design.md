# DEF-24 fix attempt: training run 13 (design)

Date: 2026-11-17. Status: option chosen by the Lead Architect in conversation ("implement the 1");
this document is waiting for the Lead Architect's review. Nothing is implemented yet.

## Why

DEF-24 (High): model 60 misses the accuracy, F1 and recall targets on unseen UNSW-NB15 data
(86.2% / 85.4% / 76.0% against 90%). 80% of the misses are Fuzzers from the official training
partition ("file 2"), caught 22.8% of the time.

A throwaway check on 2026-11-17 (scratchpad scripts, never reading the reserved final-test rows;
copied to `test-results/def24_check_20261117/` as evidence, see Records) found:

| Finding | Evidence |
|---|---|
| Unused UNSW-NB15 measurements do not help a model that has not seen file 2's Fuzzers | Trained on file 1, scored on file 2: Fuzzers 24.1% with the 16 features, at most 27.2% with any group added, 24.7% even with the excluded TTLs |
| Handshake timing (`synack`, `ackdat`, `tcprtt`) is a capture-position artifact | Dataset normal `ackdat` median 0.15 ms, attacks 58.9 ms; PC A's own connections 0.09 ms because the PC answers itself |
| `smean`/`dmean` add nothing new | Equal to bytes // packets on 100% of rows |
| File 2's Fuzzers are separable once they are in training | Only 0.05% are exact copies of a Normal row |
| Training on both files with PC A's browsing weighted 10x, plus a lower line, meets every target on a held slice of file 2 | Stacking with a histogram Gradient Boosting member: every line from 0.25 to 0.35 passes; at 0.30 accuracy 92.6%, F1 92.9%, recall 91.7%, FPR 6.4%, worst browsing recording 6.6% |
| The unchanged Stacking only scrapes through | One line (0.35), worst browsing recording 7.9% |

## Decisions

| Question | Decision |
|---|---|
| Option | Option 1: train on both files, weight PC A's browsing, stronger Gradient Boosting member, line set inside the model |
| Gradient Boosting member | Becomes scikit-learn's `HistGradientBoostingClassifier`. Its id and name stay `gradient_boosting` / "Gradient Boosting": it is the same algorithm (boosted decision trees) with binned feature values. It also replaces the stand-alone Gradient Boosting candidate, because both come from one builder |
| Combiner | Logistic Regression stays. Its intercept carries the decision line, and its weights still show how much each member counts. A Gradient Boosting combiner was considered and rejected: it would not add information, it has no single knob for the line, and it would change the method further |
| Timing | Before the tag `test-cycle-2-v1.0` |
| Order | Train and test the model before anything is released. If it fails, the code change is reverted and nothing ships |
| Thesis | The Lead Architect chose to go ahead knowing it changes the methodology and results chapters; the adviser's agreement is theirs to obtain |

## Part 1: model and app changes (release 0.6.1)

### Gradient Boosting member

`services/model_registry.py`: `build_individual_estimators()["gradient_boosting"]` becomes
`HistGradientBoostingClassifier(max_iter=400, learning_rate=0.1, max_leaf_nodes=63,
class_weight="balanced", random_state=42)`, the settings used in the check. Nothing else changes in
the registry. `MODEL_WORKFLOW_VERSION` becomes `stacking-five-v4`.

### Compatibility: a 0.6.1 PC accepts model 60 and run 13

Today a PC refuses any model whose workflow version or member types differ from its own
(`model_runtime.verify_manifest`, `services/deployment_service._validate_stacking_artifact`), and a
refused model stops detection: there is no fallback.

- `model_runtime.py`: `WORKFLOW_VERSION` (what new artifacts are stamped with) becomes
  `stacking-five-v4`; a new `ACCEPTED_WORKFLOW_VERSIONS = ("stacking-five-v3", "stacking-five-v4")`
  is what a manifest may carry.
- `_validate_stacking_artifact`: the member types are checked against the artifact's own workflow
  version: v3 needs `GradientBoostingClassifier`, v4 needs `HistGradientBoostingClassifier`. Any
  other pairing is refused, as today. `services/model_registry.py` holds that pairing
  (`GRADIENT_BOOSTING_TYPES`).
- `stacking_deployment_eligibility` accepts a training record of either version, so model 60 can
  still be deployed locally and published again.
- `publish_model.py` stamps the manifest with the artifact's own workflow version, instead of the
  constant. It refuses an artifact whose version differs from its local training record.
- `model_delivery.py` refuses an artifact whose workflow version differs from its manifest.
- No cloud database change: `model_manifest.workflow_version` is free text.

Consequences:
- PC A and PC B both install 0.6.1 before run 13 is published. A PC still on 0.6.0 shows "The
  verified model could not be loaded on this computer" once run 13 is active.
- Model 60 stays a way back. As the maintainer guide already says, "publish that local model again
  with a new ID", and every 0.6.1 PC accepts it.

### Decision line inside the combiner

- `train.py --decision-line X` (0 < X < 1, default 0.50 meaning no change), passed through
  `services/training_service.py`, applies to the Stacking Ensemble only. After the Stacking is
  fitted, its Logistic Regression intercept is shifted by `-logit(X)`. The attack score becomes
  `sigmoid(z - logit(X))`, so a score of 0.50 is exactly the old probability X. The order of scores
  and the ROC-AUC do not change.
- The check-split evaluation and the quality gate see the shifted model, so stored figures match
  what is deployed.
- The line is stored in the artifact (`decision_line`) and written to the run's event log. No
  database column is added.
- Unchanged: the verdict rule (highest class, `services/scoring_service.py`), the score bands and
  severity (`services/alert_policy.py`), the band policy in the cloud database, and both web apps.
- Meaning of the score: with a line other than 0.50, the attack score is the model's probability
  rescaled so that 0.50 is the decision line. Section 1 of `docs/MODEL_TRAINING.md` says so.

## Part 2: run 13 data and protocol

### Training file

`test-results/model_run13/build_run13_data.py` writes `research/dataset/processed/run13/training.csv`
(git-ignored):
- the run 11 training file: 66,393 file-1 rows, 2,460 PC A benign flows, 76,089 file-2 rows;
- plus the 2,460 PC A benign flows nine more times, so they count 10x. The Stacking cannot take
  sample weights because K-Nearest Neighbors cannot.

That makes 167,082 rows. It never opens `run11/final_test.csv`. A manifest with counts and SHA-256
sums goes next to the script.

### Protocol (`test-results/model_run13/protocol_run13.md`)

Committed before the data is built, with the commit of the Part 1 code it uses. Every rule below is
fixed in advance.

1. **Line choice (selection data only).** Split the 76,089 file-2 rows with
   `StratifiedGroupKFold(3, shuffle=True, random_state=13)`, grouped by the 13-feature key. The key
   is hashed with `pandas.util.hash_pandas_object`, which is the same in every process; the check
   used Python's `hash()`, which is not.
   - Each fold: train the v4 Stacking (registry and preprocessing exactly as `train.py`) on file 1,
     the PC A flows 10x and the other two folds.
   - Scores: out-of-fold scores on file 2. The fold average on the hold-out and on the four
     selection recordings (`generator`, `browser`, `final_browser`, `final_unseen`).
   - Candidate lines: 0.20 to 0.50 in steps of 0.05. A line qualifies if the out-of-fold file-2
     accuracy, F1 and recall are at least 0.90, its FPR is at most 0.08, and every selection
     recording is at most 8% Attack.
   - Choose the qualifying line with the largest smallest margin over the five limits. If none
     qualifies, stop: no final model, and DEF-24 stays a known limit.
   - The fold models see all file-1 rows, while `train.py` keeps 25% back as its check split. The
     small difference is accepted and stated.
2. **Final model.** `python train.py research\dataset\processed\run13\training.csv
   --decision-line <chosen>`. One candidate: no tuning and no second try.
3. **Gate.**
   - Each of the four selection recordings at most 8% Attack.
   - Artifact at most 50 MiB.
   - Deployment quality gate passed.

   The hold-out (file 1) is scored and reported but is not a gate. Moving the line trades file-1
   false alarms for file-2 recall; the check predicts a hold-out FPR of about 11-15% against
   run 10's 2.7%. This is a stated limit, not a hidden one.
4. **Fresh browsing.** Two new 120-second recordings on PC A after the final model exists
   (`capture_browsing.py`, once with the generator sites and once with `--sites unseen`). Each must
   be at most 8% Attack. Recording needs an administrator terminal, so the Lead Architect runs the
   two commands.
5. **Final test, once.**
   - `scripts/evaluate_model.py` with run 13's training file as `--train-csv`, on the 32,610
     reserved rows.
   - Targets: accuracy, F1 and recall at least 90%, FPR at most 8%, ROC-AUC at least 0.95.
   - Model 60 is scored on the same rows for comparison.
   - Recall per attack category, Brier score and calibration error (ECE) are reported.
6. **Ship rule.** Run 13 ships only if steps 3 and 4 pass and all five targets are met in step 5.
   Otherwise the Part 1 commits are reverted, nothing is released, model 60 stays, and DEF-24 stays
   a known limit with run 13's result recorded.

Limits stated in advance:
- The reserved rows come from file 2, which run 13 trains on, so this is a same-file test. Model
  60's figure was a cross-file test, and the two are not comparable.
- File-1 false alarms rise.
- Fuzzers recall is expected at about 70%, not 90%.
- Live evidence is benign traffic on one PC.

## Part 3: release and re-check (only if run 13 ships)

1. Version 0.6.1 in the package and `BUILD`; rebuild the analyst package.
2. PC A and PC B install 0.6.1. This is the Lead Architect's part.
3. The Lead Architect publishes run 13 with `publish_model.py` (deployment #4). Both PCs download
   and verify it.
4. TC-24 again on PC A: 10 minutes of normal browsing, at most 8% Attack.
5. SMK-01 on the published model.
6. On the final commit: the offline suites, ruff and pyright, the integration lane, the
   clean-install check and the browser walk.

If step 4 or 5 fails after publishing:
- Model 60 is published again with a new ID. Every 0.6.1 PC accepts it.
- 0.6.1 stays installed, since it runs model 60 unchanged.
- DEF-24 stays open, with run 13 recorded as withdrawn and why.

## Tests

- Registry: the Gradient Boosting member is a `HistGradientBoostingClassifier`; the workflow
  version is v4.
- Validator: accepts v3 with `GradientBoostingClassifier` and v4 with
  `HistGradientBoostingClassifier`; refuses v4 with the old type, v3 with the new type, and unknown
  versions.
- Manifest: accepts v3 and v4; refuses others. A client refuses an artifact whose version differs
  from its manifest.
- Eligibility accepts v3 and v4 records. Publishing stamps the artifact's own version and refuses
  a record/artifact mismatch.
- `model_registry.MODEL_WORKFLOW_VERSION` equals `model_runtime.WORKFLOW_VERSION`, and the pairing
  table covers exactly the accepted versions.
- Line shift:
  - a score equal to X becomes 0.50;
  - scores keep their order;
  - the default 0.50 changes nothing;
  - `--decision-line` outside (0, 1) is refused;
  - the line is stored in the artifact and the run record.
- All existing offline tests, ruff and pyright pass.

## Out of scope

New flow features, changes to score bands or the cloud database, other attack categories, further
PC B testing beyond installing 0.6.1, and tuning beyond the protocol.
