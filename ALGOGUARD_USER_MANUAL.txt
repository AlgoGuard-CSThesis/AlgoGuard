==============================================================================
PART A - USING ALGOGUARD
==============================================================================

This part covers everything you do in the website: running it, watching traffic
being classified, and predicting single flows. The model is already trained and
deployed, so this is all most users ever need.



1. WHAT ALGOGUARD DOES
----------------------

AlgoGuard is a web application that detects anomalies in network traffic using
a pre-trained Stacking Ensemble. The website only detects; the model itself is
trained separately from a terminal.

It has two detection modes:

1. Live Monitor
   Streams network flows through the deployed model one at a time and shows
   each verdict as it happens, with running attack/normal statistics, a
   timeline chart, and automatic alerts. Flows can come from three sources:
   live packet capture on a network interface, a recorded .pcap file, or the
   bundled labelled UNSW-NB15 samples.

2. Manual Prediction
   Type one network traffic example by hand and let the active deployed
   Stacking model classify it as Normal or Attack.

Retraining is done offline with train.py. The website has no upload or
training page: the finished product runs the model, it does not build it.

Important:
Live capture reads real packets from the selected network card, groups them
into flows, and classifies each flow when it ends. It needs the Npcap driver
and an Administrator terminal on Windows (see section 4). Without them the
two replay sources still work, so a demo never depends on the driver.
AlgoGuard only observes traffic: it never blocks anything and stores flow
metadata only, never packet contents. Capture only on networks you are
authorized to monitor.


2. HOW TO RUN ALGOGUARD
-----------------------

Open a PowerShell terminal in the project folder (the folder that contains
app.py and requirements.txt).

First time only (fresh clone from GitHub):

    py -m venv venv
    .\venv\Scripts\Activate.ps1
    python -m pip install -r requirements.txt
    python train.py datasets\algoguard_big.csv --deploy

The last command is required once: the trained model is not stored in Git, so
a fresh clone has no deployed model until you train one (about 20-60 seconds).
It also creates the database and prints the one-time admin password described
below. If PowerShell refuses to run Activate.ps1, run
"Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass" first, or call
.\venv\Scripts\python.exe directly instead of python.

Every time after that:

    .\venv\Scripts\Activate.ps1
    python app.py

if python is not on path, run with the existing virtual environment
.\venv\Scripts\python.exe app.py

Then open:

http://localhost:5000

The website needs no internet connection: all styling is bundled with the
project.

First local login on a new database:

Username:
admin

Password:
Read the one-time random password printed in the terminal by whichever
command created the database first (train.py, migrate.py, or app.py).

Important:
The default admin is created only when the local SQLite database is first
created. Store the generated password immediately because it is not shown again.
You can choose the first admin username/password using ALGOGUARD_ADMIN_USERNAME
and ALGOGUARD_ADMIN_PASSWORD environment variables before the first run. These
settings do not change an account already stored in the database.

After logging in with an Administrator account, open the Admins page to create
more admin accounts. Each new admin is stored in SQLite with a hashed password.
New passwords need 12 to 128 characters with upper- and lower-case letters, a
digit, and a symbol. After 5 failed sign-ins for one account (or 20 from one
computer) within 15 minutes, sign-in is paused for the rest of that window.

If port 5000 is busy (PowerShell):

$env:ALGOGUARD_PORT = "5001"
python app.py

Then open:

http://localhost:5001


3. WEBSITE PAGES
----------------

Login
    Opens the protected admin entry page. You must sign in before using the
    Dashboard, Live Monitor, or Predict pages.

Admins
    Allows an Administrator account to create and review multiple admin
    accounts.

Dashboard
    Shows the AlgoGuard overview: the deployed model and its metrics, how many
    flows have been analyzed, the attack/normal split, and recent alerts.

Live Monitor
    Streams traffic through the deployed model and shows each classification
    as it happens.

Predict
    Lets you manually type one network flow and predict if it is Normal or

    Lists every flow that was classified as an attack.

Logs
    The filterable audit trail of every action the system took.


4. LIVE MONITOR: WATCHING DETECTION HAPPEN
------------------------------------------

Open the Live Monitor page, choose the settings, then press Start Monitoring.

Traffic source
    Sample replay (labelled flows)
        Streams one of the bundled UNSW-NB15 samples: 5,000, 10,000, or
        20,000 flows. Each row keeps its true label, so the feed can show
        whether every verdict was right. This is the safest choice for a
        demonstration and needs no driver.
    Recorded packets (PCAP)
        Replays a .pcap, .pcapng, or .cap file placed in the captures/ folder.
        The packets are grouped into flows by AlgoGuard's flow tracker and
        classified at the chosen speed. Packet files carry no labels, so the
        Actual column shows a dash.
    Live interface capture
        Sniffs the selected network card in real time. A flow is classified
        when its TCP connection closes, after 15 seconds of silence, or every
        120 seconds for long connections, so the first verdicts appear a few
        seconds after Start, not instantly. Live mode runs at wire pace
        (speed and order do not apply) and shows detection lag plus captured
        and dropped packet counts. Requirements on Windows: install Npcap
        from https://npcap.com with its default "WinPcap API-compatible
        mode", and start AlgoGuard from a terminal opened as Administrator.
        If either is missing, the page says why live capture is unavailable
        and the replay sources keep working. AlgoGuard ignores its own web
        traffic so the feed does not fill with the browser polling the page.

Sample dataset / Capture file / Network interface
    The second control changes with the source: which bundled sample, which
    .pcap file, or which interface to use.

Replay speed
    Slow is one flow every 2 seconds, Normal is one flow per second, and Fast
    is roughly three flows per second. Maximum adds no delay: flows are
    classified as fast as the model allows, several at a time, which suits a
    large sample. Slower speeds are easier to narrate during a demonstration.

Flow order
    Sequential replays the file top to bottom. Randomised shuffles it first,
    so attacks and normal traffic arrive mixed together.

Storage
    "Session only" stores nothing and just shows the live feed. "Save attacks"
    (the default) stores only attack flows, each with an alert. "Save every
    flow" stores every classification. Saving stops after 300 records per
    session so the database does not grow without limit; detection continues.

While a session runs you will see:

    - A blinking LIVE indicator.
    - Counters for flows analyzed, attacks, normal traffic, and alerts raised.
    - A timeline chart where each bar is one moment in time, split into the
      normal portion and the attack portion.
    - A feed table of the most recent flows, newest at the top, showing the
      time, source and destination, protocol, service, verdict, the model's
      confidence, and (for sample replay) the true label recorded in the
      dataset. A true label shown in amber means the model got that one wrong.
      Packet sources show real addresses and ports and a dash for Actual.

Pause freezes the stream without ending the session, Resume continues it, and
Stop ends it. Refreshing your browser during a session is safe: the page
reconnects to the session that is still running.

Only one monitoring session runs at a time. If Start reports that a session is
already running, press Stop first.

The first two or three seconds after Start show the "starting" state while the
model is loaded and warmed up. This is normal.


5. PREDICT PAGE: WHAT TO TYPE
-----------------------------

Go to:

http://localhost:5000/simulation

The page builds its form from the deployed model itself, so the fields always
match what that model was trained on. The current model asks for 16 fields:

Dur             Flow duration in seconds.
Proto           Protocol, such as tcp, udp, or gre.
Service         Application service, such as http, dns, ftp-data, or - for none.
State           Connection state, such as FIN, INT, CON, or REQ.
Spkts           Packets sent by the source.
Dpkts           Packets sent by the destination.
Sbytes          Bytes sent by the source.
Dbytes          Bytes sent by the destination.
Rate            Packets per second.
Sload           Source bits per second.
Dload           Destination bits per second.
Sinpkt          Average gap between source packets, in milliseconds.
Dinpkt          Average gap between destination packets, in milliseconds.
Ct_dst_src_ltm  Of the last 100 connections, how many had this source and
                destination (1 or more).
Ct_dst_ltm      Of the last 100 connections, how many went to this destination.
Ct_srv_dst      Of the last 100 connections, how many used this service to this
                destination.

Every field is required. The page opens pre-filled with a valid example, so you
can simply change one or two values and press Run Prediction to experiment.

If you retrain on a dataset with different columns, this list changes to match
automatically. You never have to edit the form.

Spkts:          2

8. WHAT HAPPENS WHEN AN ATTACK IS DETECTED
------------------------------------------

If the Predict page or the Live Monitor classifies a flow as Attack:

1. The result card shows Attack.
2. The confidence percentage is displayed.
3. The entered flow values are shown.
4. The traffic flow is saved in the network_traffic table.
5. The model result is saved in the prediction table.
6. An alert record is created in the alert table.

Alert History lets admins review saved Attack prediction alerts directly in
the web interface. Each alert shows the source and destination of its flow
("Manual entry" for hand-typed predictions) and a severity taken from the
model's confidence: High at 90% or more, Medium from 75%, Low below 75%.

Every alert starts Open. Press Acknowledge when you start looking into it and
Resolve when it is handled; Reopen puts it back. The dashboard's Open Alerts
count only includes alerts still Open, and each change is written to the logs.


9. WHAT HAPPENS WHEN TRAFFIC IS NORMAL
--------------------------------------

If the Predict page or the Live Monitor classifies a flow as Normal:

1. The result card shows Normal.
2. The confidence percentage is displayed.
3. The entered flow values are shown.
4. The traffic flow and prediction are saved in SQLite.

This means the active Stacking model thinks the flow is closer to normal traffic
than attack traffic.


10. WHAT CONFIDENCE MEANS
-------------------------

Confidence is the model's estimated certainty.

Example:

Prediction:
Attack

Confidence:
82.50%

Meaning:
The model is 82.50% confident in the predicted class.

Important:
High confidence does not guarantee the prediction is correct. It only shows
how confident the model is based on what it learned.


11. WHAT EACH FLOW FIELD MEANS
------------------------------

These are the fields you type on the Predict page, and the same fields the Live
Monitor feed displays for each classified flow:

dur
    Short for duration.
    It represents how long the network flow lasted.

    Example:
    0.10

    A small value means the flow happened quickly.

rate
    Represents traffic rate, such as packets per second.

    Example:
    12

    A moderate value can look normal.
    A very high value, such as 5000, can look suspicious.

proto
    Short for protocol.
    It tells what network protocol was used.

    Example values:
    tcp
    udp
    icmp

state
    Represents the connection state.

    Example values:
    CON
    FIN
    REQ
    INT

    CON or FIN can look more normal.
    REQ or INT can sometimes appear in suspicious traffic depending on the
    dataset.

label
    This is the target label.
    It tells the model the correct answer for that row.

    Example values:
    normal
    attack

    Important:
    In AlgoGuard, the label column must be the last column.


12. HOW TO EXPLAIN THIS IN A PRESENTATION
-----------------------------------------

Short explanation:

AlgoGuard is a network anomaly detection system. Five machine learning models
are trained and compared for research, then combined into a Stacking Ensemble
that merges their probability outputs using Logistic Regression. Only that
Stacking model, once it passes a quality gate, is deployed. The website runs
that deployed model: the Live Monitor streams network flows through it and
classifies each one as Normal or Attack in real time, and the Predict page
classifies a single flow entered by hand.

Why training is not in the website:

Training was built into the web app during development to show how the machine
learning works. The finished product separates the two concerns: training is an
offline task run with train.py, and the website is the detector. This is how a
real deployment works, and it means a training job can never disturb or slow
down live detection.

If asked whether it monitors real traffic:

Yes. In live mode it captures packets from the network card, groups them into
bidirectional flows, computes the same 16 features the model was trained on
(13 describe the flow; 3 count recent connections to the same destination),
and classifies each flow the moment it ends. The same pipeline also replays
recorded .pcap files and the labelled UNSW-NB15 samples; the labelled replay
is what lets the Live Monitor show whether each prediction was correct, which
captured traffic cannot do because nobody has labelled it yet.

If asked what happens when an anomaly is detected:

The verdict and confidence appear immediately in the feed, the attack counter
and timeline chart update, and the traffic record, prediction record, and an
alert (High, Medium, or Low severity depending on the model's confidence) are
written to SQLite. The alert appears on the Alerts page as Open until someone
acknowledges or resolves it, and the whole sequence is recorded in the audit log.

PART B - REBUILDING THE MODEL (OPTIONAL)

You only need this part if you want to train AlgoGuard on new data. Training

15. HOW TO RETRAIN THE MODEL
----------------------------

Training is a terminal command, not a page on the website. Stop the website
first if it is running, then from the project root:

Compare the models without changing anything that is deployed:

    python train.py datasets\algoguard_big.csv

Train and then deploy the Stacking Ensemble if it passes the quality gate:

    python train.py datasets\algoguard_big.csv --deploy

Train on your own file:

    python train.py C:\path\to\my_traffic.csv --deploy

What you will see:

    - A training run number.
    - Progress as each of the six models trains.
    - A comparison table of Accuracy, F1, ROC-AUC, and the overall score.
    - The path of the saved report CSV.
    - With --deploy, confirmation that the Stacking Ensemble is now active.

Without --deploy, the model currently serving the website is left completely
untouched. This is the safe way to experiment with a new dataset.

If the quality gate fails, deployment is refused and the previous model keeps
running. That is intended: a weak model never silently replaces a good one.

After a successful deploy, start the website again and the Dashboard will show
the new model, its metrics, and the run it came from.


16. WHAT CSV DATA TO USE FOR RETRAINING
---------------------------------------

The dataset file must be a CSV file.

The last column must be the target label.

Example:

dur,rate,proto,state,sbytes,dbytes,label
0.10,12,tcp,CON,500,420,normal
0.01,5000,tcp,REQ,2000,60,attack

In this example:

Features:
    dur
    rate
    proto
    state
    sbytes
    dbytes

Target label:
    label

The target label is the answer that tells the model whether the row is normal
or attack/anomaly.


17. IMPORTANT CSV RULES
-----------------------

Rule 1:
The file must end with .csv.

Rule 2:
The file must have at least two columns:

- one or more feature columns
- one target label column

Rule 3:
The target label must be the last column.

Rule 4:
The target column must not be empty.

Rule 5:
The target column must contain at least two classes.

Rule 6:
Each class should have enough rows for training/testing.

Rule 7:
Text columns are allowed.

Example:
proto,state

Rule 8:
Numerical columns are allowed.

Example:
dur,rate,sbytes,dbytes

20. WHAT NORMAL DATA CAN LOOK LIKE
----------------------------------

Normal traffic usually has values that look moderate and consistent.

Example normal row:

dur,rate,proto,state,spkts,dpkts,sbytes,dbytes,sttl,dttl,label
0.10,12,tcp,CON,12,9,500,420,64,64,normal

Meaning:

dur
    The connection duration. 0.10 means short but not extreme.

rate
    Packets per second. 12 is a moderate value.

proto
    Protocol. tcp or udp are common.

state
    Connection state. CON or FIN can appear in normal traffic.

spkts and dpkts
    Source and destination packet counts.

sbytes and dbytes
    Source and destination byte counts.

sttl and dttl
    Time-to-live values. Normal traffic often uses reasonable TTL values such
    as 64.

label
    normal


21. WHAT ANOMALY DATA CAN LOOK LIKE
-----------------------------------

Anomaly or attack-like traffic often has unusual/extreme values.

Example anomaly row:

dur,rate,proto,state,spkts,dpkts,sbytes,dbytes,sttl,dttl,label
0.01,5000,tcp,REQ,1,1,2000,60,254,0,attack

Why this can look suspicious:

rate = 5000
    Very high packet rate.

state = REQ
    A request state that may indicate incomplete or suspicious communication.

sttl = 254
    High source TTL can appear in some attack patterns.

dttl = 0
    Destination TTL of 0 can look abnormal depending on the dataset.

sbytes much larger than dbytes
    One-sided traffic can sometimes indicate suspicious behavior.

label = attack
    This tells the training workflow that this row is an anomaly/attack.


22. GOOD CSV EXAMPLE
--------------------

dur,rate,proto,state,label
0.10,12,tcp,CON,normal
0.20,10,udp,CON,normal
0.15,11,tcp,FIN,normal
0.12,14,udp,CON,normal
0.01,5000,tcp,REQ,attack
0.02,4500,tcp,INT,attack
0.01,4800,udp,REQ,attack
0.03,5200,tcp,INT,attack


23. BAD CSV EXAMPLES
--------------------

Bad example 1: no target label

dur,rate,proto,state
0.10,12,tcp,CON
0.01,5000,tcp,REQ

Problem:
The app assumes the last column is the label, so it would treat "state" as the
target by mistake.

Bad example 2: only one class

dur,rate,proto,state,label
0.10,12,tcp,CON,normal
0.20,10,udp,CON,normal

Problem:
Only normal exists. The model needs normal and attack/anomaly.

Bad example 3: empty labels

dur,rate,proto,state,label
0.10,12,tcp,CON,
0.01,5000,tcp,REQ,attack

Problem:
The target label column has missing values.

Bad example 4: too few rows

dur,rate,proto,state,label
0.10,12,tcp,CON,normal
0.01,5000,tcp,REQ,attack

Problem:
Too few rows for a reliable train/test split.


24. WHAT HAPPENS IF YOU PUT AN ANOMALY IN THE DATASET
-----------------------------------------------------

If your CSV contains anomaly rows, AlgoGuard uses them during training and
testing.

Example:

normal rows teach the model what normal traffic looks like.
attack rows teach the model what suspicious traffic looks like.

When you run train.py, AlgoGuard:

1. Reads the CSV.
2. Treats the last column as the label.
3. Counts normal and anomaly rows.
4. Encodes text columns like proto and state.
5. Scales numerical values.
6. Splits the data into training and testing sets.
7. Trains Random Forest, Gradient Boosting, AdaBoost, K-Nearest Neighbors,
   Naive Bayes, and the Stacking Ensemble.
8. Tests each model.
9. Shows the metrics.
10. Saves model records and report metadata in SQLite.
11. Ranks the five individual models for research comparison.
12. Checks whether Stacking meets the deployment quality requirements.

If the model predicts anomaly correctly:
    Recall and F1-score may improve.

If the model predicts normal traffic as anomaly:
    False Positive Rate increases.

If the model misses actual anomalies:
    Recall may decrease.


25. WHAT HAPPENS IF ALL DATA IS NORMAL
--------------------------------------

The app will reject the dataset if the target label has only one class.

Example bad dataset:

dur,rate,proto,state,label
0.10,12,tcp,CON,normal
0.20,10,udp,CON,normal
0.15,11,tcp,FIN,normal

Why it is rejected:
The model needs at least two classes to learn classification.

Good dataset:
Must have at least:

- one normal class
- one attack/anomaly class

Also, each class should have enough rows for train/test split.


26. WHAT HAPPENS IF ALL DATA IS ATTACK
--------------------------------------

This is also invalid for training.

The model cannot learn the difference between normal and attack if it only sees
attack rows.

The dataset should contain both normal and attack/anomaly examples.

28. INDIVIDUAL COMPARISON AND STACKING DEPLOYMENT
-------------------------------------------------

AlgoGuard ranks the five individual models using nine normalized metrics:
Accuracy, Precision, Recall, F1-score, ROC-AUC, False Positive Rate, CPU time,
peak RAM increase, and model size. This ranking is for research comparison
only. The ranking is printed by train.py, but the top individual model cannot
be deployed.

Stacking uses all five model families as base learners and Logistic Regression
to combine their probabilities. It is evaluated separately and is the only
deployable prediction framework. It is the model the website runs.

By default, Stacking must complete successfully and achieve at least 70%
Accuracy, 70% F1-score, and 70% ROC-AUC. If training fails, an evaluation value
is missing, or any requirement is missed, deployment is blocked. Deployment
only happens when you pass --deploy to train.py and the gate passes:

    python train.py datasets\algoguard_big.csv --deploy

Without --deploy, train.py compares the models and leaves the running detector
completely untouched.


29. WHAT FILES ARE CREATED AFTER TRAINING
-----------------------------------------

After running train.py, the following can be generated:

saved_models/run_<run_id>/*.joblib
saved_models/deployed_model.joblib
reports/training_run_<run_id>_model_results.csv
database/algoguard.sqlite3

These generated files are ignored by Git so the repository stays clean, and
so are any .pcap recordings you place in captures/. This is why a fresh clone
must run train.py --deploy once before the website has a model.

The SQLite database stores:

admin
    Multiple admin login accounts with hashed passwords.

network_traffic
    Traffic rows created by the Live Monitor or by manual prediction. The
    dataset_source column records which one produced each row.

detection_model
    Trained model names, versions, metrics, training time, and model size.

prediction
    Prediction result, confidence score, timestamp, traffic reference, and
    model reference.

alert
    Attack/anomaly alerts created from suspicious predictions.

report
    Report metadata connected to the admin who generated the report.

report_alert
    Join table that can connect reports to one or more alert records.

system_log
    Login, logout, training, deployment, live monitoring, and prediction
    activity records.

capture_session
    One row per live interface capture: interface, start and end time,
    packets captured and dropped, and flows classified.

32. WHAT EACH SAMPLE ROW MEANS
------------------------------

Header row:

dur,rate,proto,state,label

This row names the columns. It is not a traffic record.

Normal row example:

0.10,12,tcp,CON,normal

Meaning:

dur = 0.10
    The traffic flow lasted 0.10 seconds.

rate = 12
    The traffic rate is moderate.

proto = tcp
    The flow used TCP.

state = CON
    The connection state is CON.

label = normal
    This row is marked as normal traffic.

Attack row example:

0.01,5000,tcp,REQ,attack

Meaning:

dur = 0.01
    The traffic flow was very short.

rate = 5000
    The traffic rate is very high.

proto = tcp
    The flow used TCP.

state = REQ
    The connection state is REQ.

label = attack
    This row is marked as suspicious/attack traffic.


33. HOW TO READ THE SAMPLE CSV
------------------------------

This row:

0.20,10,udp,CON,normal

Can be read as:

"A UDP network flow lasted 0.20 seconds, had a traffic rate of 10, had a CON
state, and is labeled as normal."

This row:

0.03,5200,tcp,INT,attack

Can be read as:

"A TCP network flow lasted 0.03 seconds, had a very high traffic rate of 5200,
had an INT state, and is labeled as attack."


34. WHY THE CSV NEEDS NORMAL AND ATTACK ROWS
--------------------------------------------

The model learns by comparing examples.

Normal rows teach the model:

"This is what safe traffic can look like."

Attack rows teach the model:

"This is what suspicious traffic can look like."

If the dataset only has normal rows, the model cannot learn what attack traffic
looks like.

If the dataset only has attack rows, the model cannot learn what normal traffic
looks like.

That is why a good training CSV needs both normal and attack rows.


35. FINAL REMINDER
------------------

AlgoGuard is not trying to be a complete enterprise IDS.

It is a capstone/research project that demonstrates a full detection system:

Offline, with train.py:
- preprocessing
- feature encoding and scaling
- training six models
- model comparison and ranking
- a quality gate before any model is deployed

Online, in the website:
- continuous flow-by-flow anomaly detection in the Live Monitor
- single-flow prediction on the Predict page
- automatic alerting on detected attacks
- dashboard, alert history, and a full audit trail

The separation is the point: the website runs a model that was proven good
before it was ever deployed.
